TL;DR

  • A laptop-local multimodal stack: chat, image questions, image creation, dictation and a voice assistant, with no cloud and no API key after models are downloaded.
  • One large model in RAM at a time (ModelManager). Chat, Qwen2.5-VL and SD-Turbo share the slot; Whisper and Piper stay resident.
  • Sized for an ordinary machine: the reference laptop is an Intel Core i3-N305, 7.7 GB RAM, no graphics card.
  • Also a lab: one example script per modality, and 23 guides from a single neuron to transformers to a data center.

Abstract

Running modern generative models usually assumes a GPU and a network. This project asks a narrower question: what of chat, vision-language, latent diffusion and speech still fits on a CPU-only laptop with under 8 GB of RAM, and how should the software be arranged so that constraint is visible rather than hidden? Local AI is a single-process FastAPI server and a single-file browser UI. Text and vision-language inference use llama.cpp on 4-bit GGUF weights (Qwen2.5 1.5B Instruct and Qwen2.5-VL 3B). Image generation uses SD-Turbo with a TAESD decoder on CPU PyTorch. Speech uses faster-whisper and Piper. Every feature follows the same six-stage pipeline — input, preprocess, model, inference, postprocess, output — so the examples and the 23 guides can point at the same arrows. Weights are fetched from Hugging Face only when the user asks; prompts never leave the machine. Video generation is gated because the hardware profile reports no discrete GPU. Measured on the reference laptop, chat runs at 15–19 tokens/s, a 512×512 image takes about 30 s, and voice chat answers in about 5 s after the end of speech.

Method

1. Initialization

Double-clicking run.bat creates a virtualenv, installs pinned CPU wheels, and starts app.py. The process checks /api/health so a second launch only reopens the browser. If models/ has no GGUF file, the default chat model (1.1 GB) is downloaded once. The chat model is loaded before the first request so the first token is not waiting on disk. Other weights — Qwen2.5-VL, SD-Turbo, Whisper, Piper — download only after an explicit Download action.

2. Routing and world-frame analogue: one model slot

The browser sends the whole conversation on every turn; the server is stateless. Attachments are resized in a canvas to 448 px JPEG, or a video is folded into a 2×2 grid of four frames. A conversation that contains an image is routed to the vision model; otherwise it uses the selected chat GGUF. ModelManager holds at most one large model. Switching between chat, vision and SD-Turbo takes 10–40 s. Two locks separate the large-model slot from the speech slot, so Piper can speak a sentence while llama.cpp writes the next one.

3. Compositional engines and contact with hardware

Each modality has its own engine and its own preprocess:

INPUT → PREPROCESS → MODEL → INFERENCE → POSTPROCESS → OUTPUT TEXT chat template → tokens → transformer → logits → sample VLM 448 px image → vision encoder → projector + LLM IMAGE prompt → CLIP → one-step UNet → TAESD decode STT 16 kHz WAV → log-mel → Whisper encoder/decoder TTS text → phonemes → Piper VITS → WAV

fit_context() drops old turns in large chunks so llama.cpp can reuse its prefix cache. Speech endpointing is loudness-based in an AudioWorklet at 16 kHz. hardware.video_gate() refuses video generation on this profile and returns the reason rather than starting a job that cannot finish.
